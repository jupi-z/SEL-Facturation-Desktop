# SEL V2 Backend Design

**Date:** 2026-11-02  
**Source of truth:** `CODEX_SEL_V2_BACKEND_START_HERE.md` and `Docs/SEL_V2_BACKEND/`  
**Scope:** backend only, isolated under `v2/`

## Intent

Build an autonomous Rust backend that can serve the SEL commercial domain without a graphical frontend. The same domain rules must run centrally against PostgreSQL and locally against SQLite so the Windows client can continue working offline and reconcile later without duplicating invoices, payments, receivables, or solar installment obligations.

## Goals

- Provide a standalone Axum REST API with OpenAPI 3.1, stable problem responses, RBAC hooks, idempotency, and health endpoints.
- Provide PostgreSQL migrations for the central structured ledger and SQLite migrations for the local projection, command journal, outbox, inbox, and sync cursor.
- Implement the P0 commercial vertical: customer, validated catalog, combined electricity/water invoice with mandatory zero-water line, ordinary partial payment, solar sale with one receivable and an exact installment schedule, statement, and document-data JSON.
- Keep every monetary value decimal and snapshot all tariff, tax, currency, and exchange-rate inputs at issuance.
- Implement durable offline push/pull semantics with event deduplication, explicit conflicts, and truthful local/central statuses.
- Add a signed declarative LiveUpdate verifier and a dry-run legacy migration/reconciliation CLI without allowing executable or invoice-file bundles.
- Prove the no-invoice-file server property and preserve V1 files and behavior.

## Non-goals and anti-goals

- No new frontend, Tauri shell, React application, or replacement of `app.py`/`db.py`.
- No real SEL data, production tariffs, production keys, VPS deployment, release, or migration of a live database.
- No PDF endpoint, PDF bytes, invoice image, invoice path, object-storage upload, or invoice file in logs, backups, or PostgreSQL.
- No implicit fiscal certification, DGI QR, interest, penalty, stock availability, or tax/tariff value that SEL has not supplied.
- No last-write-wins for financial records, generic CRDT, direct PostgreSQL access from Windows, or opaque third-party sync service.

## Constraints

- All implementation stays under `v2/`; V1 is read-only except for explicitly isolated test adapters.
- Central PostgreSQL is the source of consolidated truth. Local SQLite is a projection plus durable commands/outbox and must never be treated as centrally accepted before acknowledgement.
- `Idempotency-Key` is required for financial writes and sync commands.
- UUIDs are generated by the client/domain layer; provisional offline references are distinct from final numbers.
- Issued invoices and financial movements are append-only/immutable; corrections use explicit reversal/credit/void operations.
- A utility invoice always contains exactly `ELECTRICITY` and `WATER`; `0 m3` is visible with zero amount and no invented water tariff.

## Approaches considered

1. **Replace the current Flask application with Rust immediately.** Rejected because it breaks V1 compatibility, violates the isolated `v2/` requirement, and prevents a controlled migration.
2. **Split auth, billing, sync, and updates into separate services.** Rejected for the target window: it increases deployment and consistency failure modes without a required business benefit.
3. **Rust modular monolith plus local Rust agent** (chosen). It shares the domain and contracts, keeps one transaction boundary per store, permits standalone HTTP/CLI testing, and leaves the V1 client untouched until the backend is accepted.

## Chosen architecture

`v2/` is a Cargo workspace with focused crates:

- `sel-domain`: decimal money, tariff validation, invoice, payment, receivable, installment, and conflict rules.
- `sel-contracts`: versioned DTOs, problem details, sync envelopes, and OpenAPI-facing types.
- `sel-storage`: SQLx repository boundaries, PG/SQLite migrations, transaction helpers, and file-safety checks.
- `sel-sync`: outbox/inbox, idempotency, push/pull application, cursors, and conflict records.
- `sel-api`: Axum central HTTP routes and authorization boundary.
- `sel-local`: loopback-only local HTTP agent backed by SQLite.
- `sel-cli`: health, migration dry-run, reconciliation, and test scenario commands.

The first implementation uses deterministic in-memory service wiring in unit/HTTP tests and SQLx-backed integration paths behind feature/configuration gates. PostgreSQL tests run only when an explicit test database is available; they are reported as blocked rather than silently downgraded.

## Domain decisions

- Utility preview and issue accept a customer, billing period, electricity quantity, water quantity, currency, and an approved tariff revision. Positive water requires an active approved water tariff and tax profile. Zero water requires explicit confirmation and always emits a visible water line.
- Ordinary invoice payment creates one payment and allocations against the existing receivable; it never creates an installment plan.
- A solar sale creates exactly one receivable. Activating an installment plan validates that schedule amounts sum exactly to the principal and references that receivable uniquely.
- All conversions require an approved dated rate and preserve source and target amounts in the snapshot. No float types are used.
- Offline records are `LOCAL_PENDING` until a central commit is acknowledged. Retrying the same event returns the original outcome; same event ID with another payload is a security conflict.

## Verification strategy

The branch will add unit, HTTP contract, SQLite, PostgreSQL-when-available, sync interruption, adversarial update, migration dry-run, and no-invoice-file tests. The final report will enumerate every API/FIN/SYN/UPD/MIG/FILE/OPS identifier from `08_MATRICE_TESTS_ET_PREUVES.md` with `PASS`, `FAIL`, `BLOCKED_EXTERNAL`, or `NOT_TESTED`, the exact command, commit SHA, and evidence path.
